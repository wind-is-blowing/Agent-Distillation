# 09 候选池与调度

## 9.1 演进顺序

候选池不是 MVP 前置条件。推荐先完成：

```text
一个 champion
→ 一次诊断
→ 一个 challenger
→ 接受/拒绝
```

当闭环可重复、评测噪声可估计、历史查询稳定后，再启用本章的多候选搜索。

## 9.2 三个集合

### 完整历史

保存所有已评测版本，包括失败、违规和退步候选。完整历史用于复盘和提取局部组件。

### Pareto 前沿

在同一评测口径下，没有被其他候选在所有目标上同时不差且至少一项更好的版本集合。

### 活跃候选

近期获得搜索预算的少量版本。活跃候选是调度选择，不改变版本是否属于 Pareto 前沿。

这三个集合不能混为“保留”与“删除”。未激活的版本仍保留代码、分数和轨迹。

## 9.3 候选状态

```text
DRAFT
VALIDATED
SMOKE_PASSED
EVALUATED
PARETO
ACTIVE
INACTIVE
REJECTED
ARCHIVED
```

`PARETO` 和 `ACTIVE` 是可重新计算的标签；`REJECTED` 表示未通过某轮晋升，不代表其所有组件都无价值。

## 9.4 父代选择

V2 使用显式调度分数：

\[
priority(h) = w_1 \cdot gap(h) + w_2 \cdot evidence(h) + w_3 \cdot novelty(h) + w_4 \cdot staleness(h) - w_5 \cdot cost(h)
\]

- `gap`：该版本距离目标约束的改进空间；
- `evidence`：现有失败证据是否支持一个可行动假设；
- `novelty`：是否代表不同的能力/成本区域；
- `staleness`：多久没有获得优化机会；
- `cost`：完整评测它需要的资源。

权重固定在实验配置中，并保存选择原因。

## 9.5 探索与利用

每轮有两个候选名额时：

1. **利用名额**：从当前产品效用最高或证据最充分的版本出发，解决一个明确失败。
2. **探索名额**：从长期未优化的前沿版本出发，或验证一个跨版本组件组合。

例如：

```text
A：成功率高、成本高
B：成功率略低、成本低

A'：减少上下文成本
B'：在保持低成本时修复特有失败
```

系统不保证每个前沿候选每轮都被修改，但 `staleness` 可以防止某条有价值路线永久饿死。

## 9.6 Pareto 计算

只有满足硬约束、使用相同数据快照和兼容评测配置的版本才能互相支配。设成功率越大越好、成本越小越好：

```python
def dominates(a, b):
    no_worse = a.success >= b.success and a.cost <= b.cost
    strictly_better = a.success > b.success or a.cost < b.cost
    return no_worse and strictly_better
```

有统计不确定性时使用保守支配：只有当置信区间或预设显著性规则表明“不差”时才移出前沿。不能因为一次随机 trial 就删除一条路线。

## 9.7 活跃集大小

建议最多保留 3–5 个活跃代表：

- 最高能力代表；
- 最低成本代表；
- 平衡代表；
- 最近显著改善代表；
- 一个探索代表。

其余前沿版本保持 `INACTIVE`，在任务分布或目标权重变化时可以重新激活。

## 9.8 组件组合

组合候选需要明确提案：

```json
{
  "type": "component_merge",
  "base_version": "H_014",
  "sources": [
    {"version": "H_009", "component": "observation/head_tail_v2"},
    {"version": "H_014", "component": "completion/no_repeat_v1"}
  ],
  "interaction_risk": "两组件都消耗上下文预算",
  "required_ablation": true
}
```

组合后的分数必须重新测量。两个单独有效组件可能互相干扰。

## 9.9 消融与因果归因

当一个候选包含 A、B 两项改动且取得提升，后续安排：

```text
base
base + A
base + B
base + A + B
```

消融不是每个小候选都强制执行，但对于将进入组件库、影响多条路线或改动较大的版本应执行。结论标记为“整体有效”或“组件作用得到支持”，不要把总分提升自动归因到教师描述的原因。

## 9.10 停止条件

一次搜索在满足任一条件时停止：

- 达到候选评测或总成本预算；
- 连续 `N` 个有效候选没有净改善；
- 主要指标达到目标且回归、成本约束满足；
- 可行动提案持续不足；
- 任务集或基础环境发生变化，需要开启新实验世代。

停止后冻结候选、选择规则和代码，再运行最终测试集。
