# 15 实施路线与验收

## 15.1 实施原则

先证明证据链和裁决链正确，再扩大搜索智能。每个阶段都交付可运行的纵向切片，而不是先分别建设多个长期无法联调的模块。

## 15.2 阶段 0：基线冻结与任务准备

**目标：** 建立可信比较条件。

交付：

- 选择学生模型和初始 `H_000`；
- 定义 20–50 个小型编码任务及任务族标签；
- 划分搜索、冒烟、晋升和最终测试；
- 固定任务 commit、容器镜像、预算和评分脚本；
- 连续运行基线，估计成功率与成本波动。

验收：

- 任一基线分数能追溯到完整配置；
- 同一任务不会继承前一 trial 的文件；
- 基础设施失败可与 Agent 失败区分；
- 至少两次基线运行可给出方差或配对差异。

## 15.3 阶段 1：任务运行与证据链

**目标：** 单机执行任务并完整记录。

交付：

- `TrialSpec`、任务 runner 和 Docker backend；
- 统一工具执行 envelope；
- 只追加事件、JSONL、内容寻址产物；
- 任务补丁收集和 benchmark adapter；
- trace 查询 CLI。

验收：

- 强制终止控制器后可恢复 trial 状态；
- 原始工具输出和模型展示内容可对照；
- 事件序列无缺口，产物哈希可验证；
- 任务补丁能在干净评分环境重放。

## 15.4 阶段 2：教师诊断

**目标：** 从失败轨迹生成结构化、可验证提案。

交付：

- 事实聚合器和 evidence bundle；
- 只读教师工具；
- `DiagnosisProposal` schema；
- 证据、范围和防泄漏门禁；
- `needs_probe` 支持。

验收：

- 提案中的每个引用可打开到确定事件或代码；
- 教师无法写代码或读取隐藏测试；
- 至少三种典型失败能输出不同目标模块的提案；
- 证据不足时可选择不提出修改。

## 15.5 阶段 3：候选改造与验证

**目标：** 学生在隔离 worktree 中产生可运行候选。

交付：

- 固定 `H_edit` 和改造会话；
- worktree 生命周期；
- 路径与 diff 预算检查；
- harness manifest 和契约测试；
- `CandidateReport` 与不可变 commit 注册。

验收：

- 受保护路径修改会被自动拒绝；
- 候选可从 commit 在新环境重建；
- 任务模式和改造模式没有会话或工作区共享；
- 契约失败最多进行一次有界修复。

## 15.6 阶段 4：闭环晋升

**目标：** 自动完成一个 champion/challenger 迭代。

交付：

- 冒烟和晋升评测；
- 配对 scorecard；
- 版本化 promotion rule；
- 原子 champion 切换；
- 完整迭代状态机与预算。

验收：

- 相同 scorecard 和规则重放得到相同裁决；
- 评测边界结果会触发复测；
- 违规候选即使成功率高也不能晋升；
- 晋升后下一轮使用新 champion，旧版本仍可复查和回滚。

## 15.7 阶段 5：多候选与经验

**目标：** 在不丢失可解释性的前提下提高搜索覆盖。

交付：

- 完整历史、Pareto 前沿和活跃集；
- 探索/利用调度；
- 经验状态机与结构化检索；
- 组件来源和消融实验支持。

验收：

- 未激活的前沿版本不会被删除；
- 父代选择有可重放分数和原因；
- 检索结果包含反例；
- 组合候选必须重新评测。

## 15.8 阶段 6：规模化与生产验证

**目标：** 支持并发实验和真实任务灰度。

交付：

- PostgreSQL、对象存储、队列 worker；
- 更强沙箱和独立评分节点；
- OpenTelemetry、告警和成本看板；
- release、灰度、回滚流程；
- 最终测试与泛化报告。

验收：

- 节点故障不会产生重复晋升；
- 审计链覆盖敏感操作；
- 达到目标并发时事件和产物无丢失；
- 生产灰度能按任务族发现回归并一键回滚。

## 15.9 建议迭代周期

一个 8–10 周 MVP 可按以下节奏：

| 周 | 重点 |
|---|---|
| 1 | 基线、任务快照、指标和边界 |
| 2–3 | 任务 runner、沙箱、事件与产物 |
| 4 | benchmark adapter、scorecard、trace CLI |
| 5 | 教师 evidence bundle 与输出协议 |
| 6 | 改造 worktree、候选契约与门禁 |
| 7 | 冒烟、配对评测和晋升规则 |
| 8 | 端到端恢复、预算和闭环演示 |
| 9–10 | 稳定性、文档、基线实验和首个提升报告 |

实际进度取决于任务环境准备和单个 trial 时长。

## 15.10 测试策略

### 单元测试

只覆盖确定性核心：schema、哈希、预算、状态转换、支配计算、晋升规则和权限矩阵。

### 契约测试

验证 harness、模型网关、沙箱、benchmark adapter 和存储接口。

### 集成测试

使用假模型和微型 Git 仓库完成：任务执行、轨迹、教师固定响应、候选补丁、评分和晋升。

### 故障注入

在模型超时、事件写失败、容器崩溃、控制器重启和评分中断下验证恢复。

### 实证评测

真实模型的能力提升不适合用固定单元测试断言。通过冻结任务集、重复 trial 和配对 scorecard 验证。

## 15.11 MVP 完成定义

MVP 只有在下列条件全部满足时完成：

- 可以从一个配置启动完整进化轮；
- 教师提案引用真实轨迹；
- 学生只在候选副本修改白名单 harness；
- 候选经过契约、冒烟和晋升评测；
- PromotionEngine 自动生成可重放裁决；
- 接受与拒绝候选均保留完整版本和证据；
- 一次控制器中断后可以继续；
- 完成至少 5 轮真实实验，并报告提升、回归、成本和不确定性；
- 最终测试只对冻结选择运行一次。

## 15.12 首个演示场景

建议用“长工具输出导致错误尾部不可见”作为首个纵向演示：

1. 构造若干编译输出很长的任务和短输出保护任务。
2. 基线只保留输出头部，并保留完整原始日志。
3. 教师从 `raw` 与 `rendered` 差异提出头尾保留假设。
4. 学生只修改 `observation.py`。
5. 契约测试验证字节上限和短输出行为。
6. 晋升评测检查任务成功率、重复命令和成本。
7. 根据固定规则接受或拒绝。

这个场景能覆盖核心证据链，同时无需先实现复杂记忆和候选池。
